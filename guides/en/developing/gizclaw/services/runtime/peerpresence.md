# Shared presence

[Go API Reference](https://pkg.go.dev/github.com/GizClaw/gizclaw-go/pkgs/gizclaw/services/runtime/peerpresence)

`peerpresence` stores cross-Server connection state, the last observed activity and the running Workspace in the `presence` namespace of `services.peer.store`. Friend and member lists read these snapshots after relationship authorization. Queries never read `services.peer_run.store` SQL. Local connections, persisted run selection and runtime history retain their existing ownership.

## Publication and reads

Manager publishes online, offline, replacement, retirement and running-Workspace transitions. Agent Host notifies it after starting, running, stopping, stopped and error transitions; only running state carries a Workspace. Queries, audio traffic and telemetry do not publish presence. `last_seen_at` is activity observed at the last transition, rather than a continuously refreshed clock.

Publication queues a snapshot without storage I/O under Manager or Agent Host state locks. Each Peer has an independent serial writer that coalesces intermediate pending states. Each operation carries a two-second context deadline; failed writes retry the latest state after one second until successful or closed. Different Peers retain independent transition ordering and commit through bounded batch writers. Redis clients opened by Storage apply context deadlines to socket I/O; Go callers borrowing their own clients should enable that option too. Queries use ordinary KV reads: Redis read/write separation uses the reader, while writes and atomic conditions use the writer. Read errors return offline without a last-seen time and never fall back to SQL or the primary.

Manager gives every accepted connection its own `Publisher`. Initial online publication reads `owners/<peer>` at the write authority and atomically claims a token with its snapshot. Later Workspace and offline updates must match that token. After another Server or a replacement connection claims it, late updates from the old connection cannot overwrite its state; other Peers keep publishing. The Publisher retains its claim condition and fencing for the connection's entire lifetime, so deletion rollback cannot reclaim ownership after an offline worker retires. The initial claim condition survives retries, so a lost commit response cannot reclaim another connection's ownership. A connection coalesced into offline before any online attempt claims no token and preserves existing history. An online commit with a lost response is revoked only while its token still belongs to that connection. Tokens have no per-Peer heartbeat; readers still fetch only snapshots and Server leases.

Server composition uses the existing Peer KV automatically. Servers must share that physical namespace; sharing only Social KV does not share presence. Ordinary Redis, `redis.readwrite` and existing KV backends retain their configuration and require no additional service binding.

List pages use `ReadBatch` for Peer snapshots, followed by one lease per distinct Server. Both rounds share a two-second presence budget, including the optional group Workspace binding lookup. Shorter caller deadlines win. Authorization, pagination and profile lookups retain the request context. Results preserve page order; individual failures report offline without a last-seen time while successful independent snapshots remain available.

Bulk I/O uses the required [KV](/en/developing/stores/kv) method `Store.BatchGet`. TiKV uses one historical snapshot and native SDK BatchGet per batch, Redis uses native `MGET` on the selected reader, and other backends own at most eight concurrent point reads. Peer and lease rounds do not share a snapshot. Legacy Go providers exposing only single-Peer presence retain at most eight concurrent reads.

## Batched conditional publication

Each Server uses two batch writers and a bounded queue. Normally only one batch commits at a time to avoid ongoing generation-guard contention. The other writer may proceed after waiting a quarter of the existing two-second budget, isolating stalled storage calls. Writers collect only already-queued requests, with at most 128 distinct Peer transitions per transaction. An idle writer submits immediately without waiting to fill a batch. Queueing, condition checks and commit share the original two-second operation budget; the earliest caller deadline bounds the batch. Commit coordination and standby progress both retain the original caller deadline. Each serial Peer worker continues to own its connection token and transition order.

Batches retain the common Server generation condition and every Peer owner condition, atomically publishing snapshots and initial claim tokens. After definitive rejection, an authority batch read identifies the current generation and owners. Lost ownership is isolated, and still-matching Peers retry under their original atomic conditions. Bulk handoff uses bounded mutation calls. Storage errors and uncertain commits return to each Peer worker with its original claim condition. Lease renewal shares commit coordination and the original two-second budget with state batches. Startup, renewal and close use the existing generation key, preserving guard writes and write-skew protection.

TiKV `ApplyMutation` prefetches condition, record and deletion keys in the same transaction snapshot. Per-key validation and updates reuse the SDK snapshot cache instead of requiring a round trip per key. All conditions still participate in write conflict detection.

## Server lease

Each Server boot has a unique generation and renews one Server lease every ten seconds, without per-Peer heartbeats. Its default lifetime is thirty seconds. TiKV historical reads add the configured `kv.ReadDelay` window to that lifetime so healthy leases remain valid in historical snapshots. Historical reads still delay visibility of initial connections and later transitions.

Reads validate the snapshot generation, lease and absolute expiry time. A crashed Server, failed renewal or expired lease makes its Peers offline; graceful shutdown revokes the lease. A new generation fences writes, renewal and lease revocation from older processes. Servers should keep their clocks synchronized. Redis lag exceeding the lease window conservatively reports offline.

Close cancels and joins all workers without closing the borrowed KV Store. Presence is display data, not relationship authority, route ownership or delivery evidence. Notification delivery still requires the target device ACK.

## Validation

`tests/store-e2e/run_presence_benchmark.sh <new-evidence-dir> <baseline-ref> [repetitions=3] [duration=15s]` provides an opt-in comparison. Each pair uses a fresh, resource-bounded three-voter TiKV cluster; PD verifies three distinct voting peers for every Region. It has no Learner or host ports. Both variants use the same load driver and dependencies, with only the changed presence/KV production files overlaid from the baseline. Execution order alternates by repetition. Evidence includes source manifests, patches, binary hashes, logs and JSON. This manual runner is separate from normal CI and never uses production.

Defaults cover 1/120/250/500 Peers, native or added 20 ms RPC latency, and 500 Peers spread across three Servers. Each Peer waits for a real commit response before publishing its next online/Workspace/offline transition, so coalesced intermediate states cannot count as completed. Submission stops at the window boundary, followed by at most six seconds of drain. Reports retain all submissions, completions within two seconds, in-window throughput, incomplete operations, native prewrite/conflict counts and final snapshots verified by an independent client. Completed-operation p50/p95 are null when no operation completed; they do not describe incomplete requests or establish full-workload/production capacity. `PRESENCE_BENCHMARK_CASES` selects explicit `peers:delay:servers` cases.

Deterministic virtual-clock tests cover immediate idle publication, standby progress within the original budget during a stalled commit, and non-overlapping renewal/state commits across three renewal intervals under continuous publication. Batch regressions cover 127 simultaneous ownership replacements while a valid Peer commits within a bounded transaction budget, and rejection of an entire batch after generation replacement. The native TiKV presence gate also publishes online, Workspace and offline transitions for 256 distinct Peers on one Server. It adds 20 ms before real TiKV RPCs and counts prewrites including conflict retries, checking bounded completion and write amplification, cross-Server handoff, restart fencing and old-process close. This latency fixture does not establish production network performance or capacity.

`go test -race ./pkgs/gizclaw/services/runtime/peerpresence ./pkgs/gizclaw` covers expired leases, replaced Server generations, late Workspace/offline updates during cross-Server handoff, lost claim responses, disconnects, runtime transitions and cross-Manager queries with unavailable SQL. Batch tests cover lease deduplication, corruption, unknown Peers and a shared deadline across both read rounds. `tests/store-e2e/run_redis_readwrite_tests.sh` exercises real Redis primary/replica behavior. `tests/store-e2e/run_tikv_tests.sh <evidence-dir> --presence-only` verifies real Learner reads, replication lag and stalled TCP responses.
